讲解

第一步：怎么录——一个模板（2026-11-14）

类比：体育教练看比赛录像。 光看比分（总时间）不知道输在哪；回放录像，才看得到哪个回合在发呆、哪个动作慢。

from torch.profiler import profile, ProfilerActivity, schedule, record_function

with profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],   # Mac 上只有 CPU
             schedule=schedule(wait=1, warmup=1, active=3),              # 跳 1 步、热身 1 步、录 3 步
             record_shapes=True, profile_memory=True, with_stack=True) as prof:
    for _ in range(5):
        with record_function("train_step"):          # 自己给一段代码起名字，时间线上能看到
            train_step()
        prof.step()                                  # 告诉 profiler 一步结束了

print(prof.key_averages().table(sort_by="self_cpu_time_total", row_limit=10))
prof.export_chrome_trace("trace.json")               # 拖进 ui.perfetto.dev 看时间线

schedule 的意义（第 23 章纪律 3）：前几步有编译、热身、分配显存，不能录；只录稳定后的几步。

一句话：profile + schedule 跳过热身只录稳定步；record_function 给代码段命名；导出 trace 看时间线。

第二步：读表——Self 和 Total（2026-11-14）

本机实测：一个 Linear → GELU → Linear → LayerNorm 的小 MLP，batch 64，AdamW（默认实现），录 3 步：

Name                        Self CPU %   Self CPU   CPU total %   CPU total   # of Calls
aten::mm                      17.69%     1.431ms      17.70%      1.432ms        9
aten::addmm                   12.88%     1.042ms      13.83%      1.118ms        6
aten::mul_                     8.91%   720.617us       9.43%    762.426us       36
aten::lerp_                    6.30%   509.670us       6.30%    509.670us       18
Optimizer.step#AdamW.step      5.96%   481.952us      47.74%      3.861ms        3
aten::addcdiv_                 5.95%   481.092us       5.95%    481.092us       18
train_step                     5.33%   431.019us      99.47%      8.045ms        3
...
列 意思
Self 这个函数自己花的时间，不含它调用的子函数
Total 包含它调用的所有子函数
# of Calls 录的这几步里一共调用了几次

怎么读这张表：

  • train_step 的 Total 是 99%（它包住了一切），Self 只有 5%：本身不干活，只是个"文件夹"；
  • Optimizer.step 的 Total 是 47.7%：优化器更新占了一步的将近一半！它的 Self 只有 6%，时间花在下面一堆小算子里：mul_（36 次）、lerp_、addcdiv_、sqrt……都是 AdamW 公式里的逐元素运算（第 15 章），每个参数张量各发一遍；
  • aten::mm / addmm 是矩阵乘（前向和反向），这才是"有用的"计算。

规律：按 Self 排序找"谁在真正花时间"，按 Total 排序找"哪一大块代码慢"。

一句话：Self 是自己干的、Total 含子函数；一个小 Total 大 Self 小的条目，说明它下面有一堆碎活。

第三步：改一处、再测（2026-11-14）

诊断：AdamW 的默认实现给每个参数张量发一串小算子，碎而多。第 15 章说过 fused=True 把整个更新公式合成一个 kernel。只改这一处：

opt = torch.optim.AdamW(model.parameters(), fused=True)

实测（各录 10 步取平均）：

每步总时间 其中优化器 优化器占比
默认 2.61 ms 1.25 ms 47.9%
fused=True 1.82 ms 0.51 ms 27.9%

一行改动，每步快了 30%。（这是 CPU 上的数；GPU 上 kernel 启动开销更大，fused 的收益通常更明显。）然后回到第一步：现在最大的块是什么？—— matmul 了，那就该看第 26 章的精度和形状。

一句话：找到最大的块 → 只改它 → 再测；默认 AdamW 在小模型上可能占一半时间，fused 一行解决。

第四步：读时间线——找空白、找碎块、找等待（2026-11-14）

表格是"总账"，时间线是"录像"。把 trace.json 拖进 ui.perfetto.dev（或 chrome://tracing），GPU 训练时能看到 CPU 线程和 GPU stream 两排：

时间线上看到 说明什么 去哪章
GPU 那排有大段空白 GPU 在等：数据、同步点、CPU 下单太慢 第 25 章
CPU 那排有长条 cudaStreamSynchronize / aten::item 同步点，CPU 在等 GPU 第 5、25 章
GPU 上密密麻麻的细条 很多小 kernel，启动开销占比高 第 28 章（compile / CUDA Graph）
很多 elementwise / vectorized_* kernel 访存受限的逐元素运算 第 29 章（融合）
ncclKernel_* 长条，且和计算不重叠 通信没藏住 第 18–21 章
内存曲线（profile_memory=True）尖峰 激活或临时张量占显存 第 27 章

更底层的工具：Nsight Systems（nsys profile python train.py）能看到 CPU、GPU、NCCL、内存拷贝、操作系统调度的统一时间线；在代码里用 torch.cuda.nvtx.range_push("forward") / range_pop() 打标记，时间线上就有自己命名的区间（AISPE ch13 第 19–130 行、第 292–380 行）。单个 kernel 的细节（访存效率、占用率）用 Nsight Compute（CUDA 讲义第 9 章）。

一句话：时间线上找空白（在等）、找细碎条（太碎）、找没重叠的 NCCL；更细用 Nsight Systems + NVTX。

怎么看：

  1. 一步训练画成一条时间线：前向、反向、优化器三段，按本章实测的比例；
  2. 默认 AdamW：优化器段是一长串细碎的小块（每个参数张量一串 mul_ / lerp_ / addcdiv_ …）；
  3. 切到 fused：优化器段变成一大块，总长度变短；下方显示每步时间 2.61 → 1.82 ms。

数学原理

  • Amdahl 定律：某部分占总时间比例 \(p\)，把它加速 \(s\) 倍，总加速比 \(\frac{1}{(1-p) + p/s}\)。优化器占 47.9%、加速约 2.45 倍（1.25 → 0.51 ms）：\(\frac{1}{0.521 + 0.479/2.45} ≈ 1.40\)，和实测 2.61 / 1.82 ≈ 1.43 吻合。先改占比大的就是这个公式的结论。
