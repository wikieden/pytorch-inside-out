讲解

第一步：显存的四块（2026-11-14）

块 大小 随什么变
参数 + 梯度 + 优化器状态 混合精度 AdamW 约 16Ψ 字节（第 19 章） 只随模型大小
激活（为反向存下来的中间结果） 随 b × s × h × L 增长 batch、序列长度、层数
临时缓冲 算子运行时的工作空间、通信缓冲 实现细节
碎片 缓存分配器里用不上的零碎空块（第 5 章） 分配模式

为什么激活会很大：第 4 章说过，前向时记账员要把反向需要的张量存下来。每一层、每个 token、每个隐藏维度都要存几份。Playbook 第 350 行起给了 Transformer 每层激活的估算，大约是

\[\text{每层激活字节} \approx s \cdot b \cdot h \cdot \left(34 + \frac{5 a s}{h}\right)\]

（a 是头数；括号第二项来自 attention 的 s × s 分数表，用 FlashAttention 就几乎没了，第 14 章。）

数字演示：7B 模型（h = 4096，L = 32），b = 1、s = 4096，只看第一项：\(4096 \times 1 \times 4096 \times 34 ≈ 570\) MB 每层，32 层约 18 GB——而 7B 的 bf16 参数才 14 GB。序列翻倍，激活翻倍。

一句话：显存 = 模型状态（16Ψ）+ 激活（随 b·s·h·L）+ 临时 + 碎片；长序列时激活常常比参数还大。

第二步：激活重计算——用算力换显存（2026-11-14）

类比：考试抄笔记。 原来每道题的草稿都留着（存激活），桌子堆满了。现在只留每一大题的题目（每块的输入），要用到某道题的草稿时，照着题目再算一遍。

from torch.utils.checkpoint import checkpoint
for block in blocks:
    h = checkpoint(block, h, use_reentrant=False)    # 前向只存 block 的输入；反向时重跑 block 的前向

实测（8 个 MLP 块：Linear(1024 → 4096) → GELU → Linear(4096 → 1024)，batch 32，float32；用 torch.autograd.graph.saved_tensors_hooks 统计为反向存下的字节数，不算参数本身）：

存下的激活
不重计算 9.125 MB：每块 1.125 MB（输入 0.125 + 第一层输出 0.5 + GELU 输出 0.5）× 8，加 loss 的 0.125
每块 checkpoint 1.125 MB：每块只存输入 0.125 MB × 8，加 0.125

省了 8 倍。代价：反向时每块要再跑一次前向，大约多 1 / 3 的计算（前向 2N、反向 4N，再加一次前向 2N，第 23 章）。

选择性重计算（Playbook 第 387 行起）：不必整块重算。attention 的 softmax 输出这类"大但便宜"的激活才重算，矩阵乘的输出（贵）照样存。FlashAttention 本身就在反向里重算分数表，所以已经是一种选择性重计算。PyTorch 2.4+ 也有自动选择的 API（torch.utils.checkpoint 的 selective / create_selective_checkpoint_contexts）。

一句话：checkpoint 只存每块的输入、反向时重算，实测 8 块 MLP 激活 9.1 MB → 1.1 MB；多约 1/3 计算；选择性重算只重算便宜的。

第三步：看清是谁——memory snapshot（2026-11-14）

OOM 时别猜，录一份显存快照：

torch.cuda.memory._record_memory_history(max_entries=100_000)   # 开始记录每次分配和释放（带调用栈）
for _ in range(3): train_step()
torch.cuda.memory._dump_snapshot("snap.pickle")
torch.cuda.memory._record_memory_history(enabled=None)          # 停止

把 snap.pickle 拖进 pytorch.org/memory_viz，看到一张"显存随时间变化"的堆叠图，每一块颜色是一次分配，点它能看到是哪行代码分配的。

典型形状：前向时显存一路上升（激活越存越多），在前向结束、反向开始处达到峰值，反向时一路下降（激活用完就释放），优化器 step 时再有一个小台阶（AdamW 的临时张量）。

AISPE ch13 第 1377–1545 行有完整的分析示例；快速看数字用 torch.cuda.max_memory_allocated() 和 torch.cuda.memory_summary()。

一句话：_record_memory_history + _dump_snapshot + memory_viz 看是哪行代码占的；正常形状是前向涨、反向落。

第四步：OOM 了按什么顺序省（2026-11-14）

按"投入产出比"排（多机报告 §6）：

顺序 手段 省的是 代价
1 bf16 混合精度（第 26 章） 激活减半 几乎没有
2 FlashAttention / SDPA（第 14 章） s × s 分数表 几乎没有
3 减小 micro-batch + 梯度累积（第 9、18 章） 激活 小 batch 时 GPU 吃不饱
4 选择性 / 全量激活重计算 激活 多 0 ~ 1/3 计算
5 FSDP / ZeRO（第 19 章） 参数、梯度、优化器状态 通信
6 融合 cross-entropy（不写出 b × s × V 的 logits） 输出层激活（V 很大时巨大） 要用专门 kernel（Liger-Kernel 等，第 29 章）
7 CPU offload（OffloadPolicy） 优化器状态挪到 CPU 很慢，最后手段
另 PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True 碎片 几乎没有

一句话：先 bf16 和 Flash，再减 batch 加累积，再重计算，再 FSDP；logits 太大用融合 CE；offload 最后。

动画演示：一步训练的显存曲线

可交互版：animations/27-memory-curve.html。开关：激活重计算 开 / 关；滑块调层数。

怎么看：

  1. 底部灰色是模型状态（参数 + 梯度 + 优化器，固定）；
  2. 前向时每过一层，激活（蓝）往上叠一块；峰值在前向结束处；
  3. 反向时每层的激活被用掉、释放，曲线回落；
  4. 打开重计算：每层只叠一小块（输入），反向时临时叠一块"重算的激活"再释放；峰值明显变低，但反向变长。

数学原理

  • 重计算的算力代价：前向 \(F\)、反向 \(2F\)；全量重计算多一次前向，总量 \(3F \to 4F\)，多 \(1/3\)。
  • √L 策略：每 \(\sqrt{L}\) 层存一次，激活显存从 \(O(L)\) 降到 \(O(\sqrt{L})\)，代价仍是约一次额外前向（Chen 2016）。

讲义 公式 / 说法 写法 跑出来

关键几行：

with torch.autograd.graph.saved_tensors_hooks(pack, unpack):
    h = checkpoint(blk, h, use_reentrant=False)   # 只存输入，反向时重算

代码里才看得到的 2 件事：

  1. 统计时去掉了参数本身：Linear 的反向也要用权重，但权重本来就在显存里，不算激活。
  2. 重算时存下的张量 hook 看不到：它们在反向里临时出现、用完就丢，所以 checkpoint 只统计到输入。

自己改一改（不影响练习答案）：

  • saved_activation_mb(False, L=16)，看是不是线性增长。
  • 只对偶数层用 checkpoint，看结果在两者之间。
