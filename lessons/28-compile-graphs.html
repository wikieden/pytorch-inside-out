讲解

第一步：碎活的代价——一次实测（2026-11-14）

第 5 章说过：每个算子都要 CPU 下一次单（kernel launch），单子本身有开销。算子很小时，下单比做菜还贵。

实测（本机 CPU）：一个函数做 20 次 x = x * 1.01 + 0.01（40 个小算子），x 只有 64 个数：

每次调用
eager 30.7 µs
torch.compile 3.8 µs

快了约 8 倍。生成的代码里只有一个 kernel：cpp_fused_add_mul_0——40 个算子融成一个。时间几乎全省在"每个算子过一遍 Python 和分派器"上（第 1、3 章）。

GPU 上同理，而且多一层：即使 compile 把算子融合了，每个 kernel 还要 CPU 发一次 launch（每次几微秒）。模型小、batch 小、推理 decode 时，GPU 算一个 kernel 也就几微秒，launch 开销就成了大头。

一句话：小算子多时，时间花在"下单"而不是"做菜"；compile 融合减少单数，CUDA Graph 再把剩下的单一次下完。

第二步：训练里 compile 套在哪（2026-11-14）

套法 写法 优点 缺点
整个模型 model = torch.compile(model) 优化空间最大 编译慢（几十层要几分钟）；一处断图影响全局
区域编译（每个块） for b in model.layers: b.compile() 相同的块只编一次、全部复用，冷启动快很多（AISPE ch13 第 903 行） 块与块之间不能融合
损失 + 优化器单独 torch.compile(loss_fn)、opt.step 也可编 输出层 + CE 常是热点 —

大模型训练（torchtitan 等）常用区域编译：Transformer 的 32 层结构一样，编一次就行。和 FSDP2 一起用时，通常先 fully_shard 再对每层 compile（或顺序反过来，按框架文档）。

避免重编译（第 6 章第四步）：

  • 变长序列 → 补齐到几个固定长度（"分桶"：256、512、1024…），或者 torch._dynamo.mark_dynamic(x, 1) 告诉编译器第 1 维会变；
  • 不要在编译区里读会变的 Python 全局变量（比如当前 step 数），作为张量传进去；
  • 训练 / 评测切换（train() / eval()）会触发一次重编译，正常；
  • 用 TORCH_LOGS=recompiles 看原因。

一句话：大模型训练常按块区域编译，同构的块只编一次；变长输入补齐分桶或标 dynamic；用日志查重编译原因。

第三步：CUDA Graph——录一次，重放很多次（2026-11-14）

类比：点套餐。 原来每道菜单独点（每个 kernel 单独 launch）；CUDA Graph 是把一整套菜录成一个套餐号，以后只喊一次"3 号套餐"，后厨按录好的顺序一口气做完。

g = torch.cuda.CUDAGraph()
static_x = torch.randn(B, D, device="cuda")          # 输入要提前放在固定的位置
# 热身几次（在旁路 stream 上），让分配器把要用的显存准备好
with torch.cuda.graph(g):                            # 录：这里面的 kernel 只记录、不执行
    static_y = model(static_x)

for batch in data:
    static_x.copy_(batch)                            # 新数据拷进同一个地址
    g.replay()                                       # 一次 launch 跑完整张图
    out = static_y.clone()                           # 结果也在固定地址，要留着就 clone

（AISPE ch13 第 1266–1330 行。）

限制（录下的是"在哪个地址、做哪些 kernel"，所以）：

限制 原因
形状固定 不同形状要不同的 kernel 参数，要么为每种形状录一张图
输入输出地址固定 只能 copy_ 进去、从固定张量读出来
图里不能有同步点、CPU 逻辑 .item()、print、Python if 都不会被录进去
图里不能新分配显存 热身时分配好，录的时候复用
随机数要特殊处理 PyTorch 已为 dropout 等做了支持

省事的办法：torch.compile(model, mode="reduce-overhead") 自动用 CUDA Graph（cudagraph trees，管理多张图和它们的显存），自动处理热身和静态缓冲。遇到不满足条件的地方会跳过不录（用日志看 "skipping cudagraphs" 原因）。

一句话：CUDA Graph 把一串 kernel 录成一个，之后一次 launch 重放；要求形状和地址固定、不能有同步和新分配；reduce-overhead 模式自动帮你做。

第四步：什么时候值得（2026-11-14）

场景 compile（融合） CUDA Graph
大模型、大 batch 训练 ✓ 融合逐元素运算、省显存流量 收益小（每个 kernel 本来就够大）
小模型、小 batch 训练 ✓ ✓ launch 开销占比大
LLM 推理 decode（每步一个 token） ✓ ✓✓ 最典型的场景（第 30 章）
形状经常变 要处理动态形状 要为每种形状录图，或不用

判断依据：profiler 时间线（第 24 章）上 GPU 那排是不是密密麻麻的细条、中间有空隙——是，就是 launch 受限，上 CUDA Graph。

一句话：大 batch 训练靠融合；小 batch 和推理 decode 再加 CUDA Graph；时间线上细条加空隙就是信号。

动画演示：逐个 launch vs 一次重放

可交互版：animations/28-cuda-graph.html。三档：eager / compile（融合）/ compile + CUDA Graph；滑块调每个 kernel 的计算时间（小 batch ↔ 大 batch）。

怎么看：

  1. CPU 一排是 launch（每个淡色小块是一次下单），GPU 一排是 kernel；
  2. eager：40 个小 kernel，每个前面都要等 CPU 下单，GPU 上全是空隙；
  3. compile：融成几个 kernel，单数大减；
  4. CUDA Graph：CPU 只下一次单，GPU 上 kernel 首尾相接；
  5. 把计算时间调大（大 batch），三种方式差距变小。

口诀

小算子多时下单比做菜贵，compile 融合减单数；
大模型按块区域编，同构只编一次，变长输入补齐分桶；
CUDA Graph 录一次套餐号，形状地址要固定、不能同步和新分配；reduce-overhead 自动录；细条加空隙就该上。

数学原理

  • launch 受限的条件：每个 kernel 的 GPU 时间 \(t_k\) 小于 CPU 下单时间 \(t_l\) 时，GPU 利用率约 \(t_k / t_l\)；CUDA Graph 把 n 次下单变成 1 次，总时间从约 \(n \cdot \max(t_k, t_l)\) 降到约 \(t_l + n \cdot t_k\)。

写法 意思

torch._dynamo.mark_dynamic(x, dim) 标记会变的维度
torch.cuda.CUDAGraph() + with torch.cuda.graph(g): + g.replay() 手动 CUDA Graph
torch.compile(m, mode="reduce-overhead") 自动 CUDA Graph
