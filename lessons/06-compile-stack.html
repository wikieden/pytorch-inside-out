讲解

第一步：eager 的代价——一步一张单、一步一趟显存（2026-11-14）

eager（急切模式）= 第 1 章那样，每行代码立刻走一遍"前端 → 分派器 → kernel"。它好调试，但有两笔开销：

  1. Python 和分派器的开销：每个算子都要过一遍 Python 和分派器，大约几微秒。GPU 上一个小算子可能只要几微秒，下单比做菜还慢。
  2. 不会合并：y = (x.sin().cos() * 2).sum(-1) 在 eager 下是 4 个 kernel。每个 kernel 都从显存读一遍输入、写一遍输出：
kernel 读 写
sin x t1
cos t1 t2
mul t2 t3
sum t3 y

中间的 t1、t2、t3 只是"过路的"，写进显存再读出来纯属浪费。逐元素运算的时间几乎都花在读写显存上（第 29 章细讲），所以 4 个 kernel ≈ 4 倍的显存流量。

类比：做沙拉。 eager 像每切一样菜都放回冰箱，下一步再拿出来；合并以后是拿出来一次，在案板上切完拌完再装盘。

一句话：eager 每个算子一张单、一趟显存；中间结果来回搬是主要浪费。

第二步：三道工序——抓图、配反向、生成代码（2026-11-14）

torch.compile(f) 第一次被调用时，按顺序做三件事：

你的 Python 函数
 │ ① TorchDynamo：看着 Python 字节码执行，把张量运算一条条抄成一张图（FX Graph）
 ▼
FX 图 + guards（"这张图在什么条件下能复用"的检查清单）
 │ ② AOTAutograd：提前把反向图也推出来，前向 + 反向一起交给下一步
 ▼
只含基础算子的图（ATen / Prims IR）
 │ ③ TorchInductor：决定哪些算子合并成一个 kernel，生成代码
 ▼
GPU：Triton kernel（第 32 章）　CPU：C++ 代码（带 OpenMP 多线程和向量化）

① Dynamo（抓图）：它不改你的代码，而是在 Python 执行字节码时"旁听"，遇到张量运算就记进图里，遇到普通 Python（算个下标、拼个字符串）就当场算掉。同时记下 guards（守卫）：输入的形状、dtype、设备……下次调用先查清单，全对就直接用编好的代码。AISPE ch14 第 40–208 行。

② AOTAutograd（配反向）：训练时还要反向。它在编译时就把第 4 章那张"账本"推出来，变成一张反向图，前向和反向一起优化（比如前向少存几个中间结果、反向重新算，第 27 章）。还会把原地修改改写成不原地的版本（functionalize，函数化），方便后面优化。AISPE ch14 第 209–246 行。

③ Inductor（生成代码）：把能合并的逐元素、规约运算融合进一个 kernel，再生成代码；矩阵乘法通常还是调现成的库（cuBLAS 等），开了 mode="max-autotune" 会再试几种 Triton 实现挑最快的。AISPE ch14 第 298–441 行。

实测（本机 CPU）：上面那个 4 个算子的函数，编译后生成的代码里只有一个 kernel：

from torch._inductor.utils import run_and_get_code
_, code = run_and_get_code(torch.compile(lambda x: (x.sin().cos() * 2).sum(-1)), x)
# 生成的代码里唯一的 kernel 名叫：cpp_fused_cos_mul_sin_sum_0

名字里 fused（融合）后面把四个算子都列上了。

一句话：compile = Dynamo 抓图 → AOTAutograd 配反向 → Inductor 融合生成代码；第一次调用编译，之后查 guards 直接复用。

第三步：断图——Dynamo 抄不下去的地方（2026-11-14）

有些代码 Dynamo 没法抄进一张图，只好把图切断：前半段编一张图，回到普通 Python 执行这一句，再从后面接着抄。这叫 graph break（断图）。

最常见的原因：Python 的 if 依赖张量的值。

def g(x):
    y = x.sin()
    if y.sum() > 0:        # 要知道真假，必须先把数算出来（第 5 章的同步点）
        y = y * 2
    return y.cos()

torch._dynamo.explain(g)(x)
# graph_count = 2, graph_break_count = 1
# 原因：generic_jump TensorVariable()   ← "根据一个张量跳转"

对比没有 if 的 f：graph_count = 1, graph_break_count = 0。

断图的代价：两段之间不能融合；中间回 Python 可能有同步；断得多了，几乎回到 eager。

常见的断图原因和改法：

原因 改法
依赖张量值的 if / while torch.where(cond, a, b)（两边都算，再按条件选；第 12 章）
print、.item()、.tolist() 挪到编译函数外面，或只在调试时打开
调用 Dynamo 不认识的第三方库 / C 扩展 用 torch.library 注册成算子（第 33 章），或 torch.compiler.disable 标出来
输出大小依赖数据（nonzero、布尔索引） 改成固定形状的 mask 运算

查断图：torch._dynamo.explain(f)(x)，或运行时设环境变量 TORCH_LOGS=graph_breaks；torch.compile(f, fullgraph=True) 让断图直接报错，强迫自己改干净。AISPE ch14 第 674–1108 行。

一句话：Dynamo 抄不下去就断图；最常见的是"看张量的值决定走哪条路"，用 torch.where 改写。

第四步：重编译——guards 不通过就再编一次（2026-11-14）

guards 是"这份编好的代码适用于什么输入"。输入一变，guards 不通过，就要重编译（recompile）。

实测：

ch = torch.compile(lambda x: x * 2)
ch(torch.randn(4)); ch(torch.randn(8)); ch(torch.randn(16))
# TORCH_LOGS=recompiles 只打出一次：
# Recompiling function ... triggered by: tensor 'x' size mismatch at index 0. expected 4, actual 8

为什么 16 没再编？第一次按"长度正好是 4"编（静态形状）；看到 8 时 PyTorch 发现长度在变，第二次就编成动态形状（长度是个符号 s0，任意值都能用），16 直接复用。

重编译的常见来源：形状变（变长序列）、dtype 变、model.train() / eval() 切换、函数里读了一个会变的 Python 全局变量。编译很慢（几秒到几分钟），反复重编译会比 eager 还慢。默认重编译次数有上限，超过就放弃编译回到 eager。

三种模式（AISPE ch13 第 826 行起有对比表）：

mode= 做什么 适合
"default" 融合 + 生成代码 一般训练
"reduce-overhead" 再套 CUDA Graph，一次下整张图的单（第 28、30 章） 小 batch、推理 decode
"max-autotune" 对 matmul 等试多种实现挑最快，编译更久 形状固定、长时间跑的任务

一句话：guards 不通过就重编译；形状在变的输入第二次会编成动态形状；mode 选省开销还是多调优。

怎么看：

  1. 上面是四个算子 sin → cos → ×2 → sum；下面是显存，每个箭头是一次读或写；
  2. eager：每个算子一个 kernel，中间结果写回显存再读出来；
  3. compile：Dynamo 抄成一张图，Inductor 合成一个 kernel，只读 x、只写 y；

数学原理

  • 融合省下的显存流量：\(k\) 个逐元素算子、每个读写 \(n\) 个元素，eager 约 \(2kn\) 次读写，融合后约 \(2n\)，省到约 \(1/k\)。
  • 编译何时划算：编译耗时 \(C\)，每步省 \(\Delta\)，跑 \(N\) 步；\(N \Delta > C\) 才赚。短实验、频繁重编译时可能亏。
